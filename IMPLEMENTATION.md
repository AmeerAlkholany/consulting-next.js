# Implementation Plan — Psychological Consultation Booking Platform

**Status:** Plan only. Nothing in this document has been implemented.
**Companion documents:** [ARCHITECTURE.md](./ARCHITECTURE.md) (the design this plan realizes) and [ADR.md](./ADR.md) (why each choice was made).

## How to execute this plan

1. **Execute one step at a time, in order.** The steps are dependency-ordered; a later step assumes every earlier step is finished and merged.
2. **Stop after each step.** Report what was built, what was verified, and anything that deviated from the plan. Wait for the word `continue` before starting the next step.
3. **Do not skip ahead** and do not bundle steps, even when a later step looks trivial. The dependencies are real.
4. **No placeholders.** Every step ends with working behaviour backed by the real database and the real rules. No `TODO`, no mock service, no hard-coded array standing in for a query.
5. **Install dependencies only in the step that needs them,** with pnpm, pinned in `package.json`, lockfile committed.
6. **Every step must end green:** `pnpm lint`, `pnpm typecheck`, and `pnpm test` (from Step 2 onward) all pass before the commit.
7. **Read [ARCHITECTURE.md](./ARCHITECTURE.md) before each step.** If a step's instructions and the architecture disagree, stop and flag it rather than guessing.
8. **This is Next.js 16.** Request APIs are async, `proxy.ts` replaces `middleware.ts`, `revalidateTag` takes a second argument, `updateTag` is Server-Action-only, Turbopack is the bundler. Verify any unfamiliar API against `node_modules/next/dist/docs/` before using it.
9. **Commit messages follow Conventional Commits** (`type(scope): subject`, imperative mood, 72 characters or fewer in the subject). Each step's expected message is given; adjust the subject if the step's actual content shifted, but keep the type and scope.
10. **`AGENTS.md` is regenerated by `next dev`.** If it reappears as an uncommitted change, commit it with the step's work rather than reverting it.

## Business rules the whole plan must uphold

| #     | Rule                                                                                                                                |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------- |
| BR-1  | A user has exactly one role: `CLIENT`, `CONSULTANT`, or `ADMIN`. Only client and consultant are self-selectable at registration     |
| BR-2  | A consultant is discoverable and bookable only when `verificationStatus = APPROVED` and the user is `ACTIVE`                        |
| BR-3  | Only an admin can approve, reject, suspend, or reinstate a consultant                                                               |
| BR-4  | A client can book only a slot the consultant has actually published and that is still free                                          |
| BR-5  | Two overlapping `PENDING`/`CONFIRMED` appointments can never exist for the same consultant, or for the same client                  |
| BR-6  | No appointment may be created in the past, or inside the consultant's minimum lead time                                             |
| BR-7  | Appointment status transitions follow the state machine in ARCHITECTURE.md §18; terminal states never change                        |
| BR-8  | Client cancellation is subject to the consultant's cancellation window; consultants and admins may cancel any time before the start |
| BR-9  | Only the client who attended a `COMPLETED` appointment may review it, once, within the review window                                |
| BR-10 | A consultant sees only their own appointments, availability, and clients; a client sees only their own appointments                 |
| BR-11 | An admin sees appointment metadata but never `clientNote` or private `AppointmentNote` content                                      |
| BR-12 | Suspending a _user account_ revokes all of that user's sessions immediately                                                         |
| BR-13 | Every consequential admin action writes an `AuditLog` entry                                                                         |
| BR-14 | Booked time wins over availability edits: a rule change that would orphan an existing appointment is rejected                       |
| BR-15 | Every instant is stored in UTC; every displayed time names its timezone                                                             |

# Step 3 — Database, Prisma schema, and seed

**Objective.** Model the entire domain in Prisma, create the initial migrations including the hand-written constraint SQL, and seed deterministic development data.

**Why it is needed.** Every feature from Step 4 onward reads or writes these tables. Modelling the whole schema once — rather than growing it per feature — avoids a chain of migrations that rewrite each other, and lets the exclusion constraints exist before any booking code does.

**Dependencies.** Step 1 (environment handling). Independent of Step 2, but sequenced after it so the first feature step has both.

**Files created or modified.**

- Dependencies: `prisma` (dev), `@prisma/client`, `tsx` (dev, for the seed).
- Created: `prisma/schema.prisma`, `prisma/migrations/<ts>_init/migration.sql`, `prisma/migrations/<ts>_constraints/migration.sql`, `db/client.ts`, `db/seed.ts`, `docker-compose.yml` (local PostgreSQL 16), `tests/helpers/db.ts`.
- Modified: `package.json` (`db:migrate`, `db:deploy`, `db:studio`, `db:seed`, `db:reset` scripts and the `prisma.seed` entry), `.env.example` (`DATABASE_URL`, `DIRECT_URL`, `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`), `config/env.ts`, `.github/workflows/ci.yml` (start PostgreSQL, run `prisma migrate deploy`).

**Database changes.** Everything in ARCHITECTURE.md §8: the enums (`UserRole`, `UserStatus`, `VerificationStatus`, `ConsultationType`, `AppointmentStatus`, `CancelledBy`, `AvailabilityExceptionType`, `NotificationType`, `NoteVisibility`, `OutboxStatus`, `AuditAction`, `VerificationTokenType`) and the models (`User`, `Session`, `VerificationToken`, `ClientProfile`, `ConsultantProfile`, `Qualification`, `Specialization`, `ConsultantSpecialization`, `Language`, `ConsultantLanguage`, `ClientLanguage`, `AvailabilityRule`, `AvailabilityException`, `Appointment`, `AppointmentNote`, `Review`, `Notification`, `EmailOutbox`, `AuditLog`), with every index, unique constraint, and cascade or restrict rule specified there.

A second migration, generated with `prisma migrate dev --create-only` and then hand-edited, adds what the Prisma schema language cannot express:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE "Appointment" ADD CONSTRAINT "appointment_consultant_no_overlap"
  EXCLUDE USING gist ("consultantProfileId" WITH =,
                      tstzrange("startsAt", "endsAt", '[)') WITH &&)
  WHERE (status IN ('PENDING', 'CONFIRMED'));

ALTER TABLE "Appointment" ADD CONSTRAINT "appointment_client_no_overlap"
  EXCLUDE USING gist ("clientProfileId" WITH =,
                      tstzrange("startsAt", "endsAt", '[)') WITH &&)
  WHERE (status IN ('PENDING', 'CONFIRMED'));

ALTER TABLE "Appointment" ADD CONSTRAINT "appointment_end_after_start"
  CHECK ("endsAt" > "startsAt");

ALTER TABLE "AvailabilityRule" ADD CONSTRAINT "rule_minutes_valid"
  CHECK ("startMinute" >= 0 AND "endMinute" <= 1440 AND "startMinute" < "endMinute");

ALTER TABLE "Review" ADD CONSTRAINT "review_rating_range"
  CHECK (rating BETWEEN 1 AND 5);

ALTER TABLE "ConsultantProfile" ADD CONSTRAINT "consultant_price_positive"
  CHECK ("sessionPriceMinor" > 0);

CREATE INDEX "notification_unread_idx" ON "Notification" ("userId") WHERE "readAt" IS NULL;

CREATE INDEX "consultant_search_idx" ON "ConsultantProfile"
  USING gin (to_tsvector('english', headline || ' ' || bio));
```

If the target PostgreSQL rejects `btree_gist`, stop and report. Do not silently fall back — the downgrade documented in ARCHITECTURE.md §18 is an operator's decision, not the implementer's.

**API changes.** None.

**UI changes.** None.

**Business logic.** `db/client.ts` exports a `PrismaClient` singleton held on `globalThis` in development so hot reload does not exhaust connections, with `server-only` at the top and query logging routed to `server/logger.ts`. `db/seed.ts` is idempotent (upsert by natural key) and creates: one admin from `SEED_ADMIN_EMAIL` with a forced password reset on first sign-in (so the seed never needs the Step 4 hashing module), roughly 20 specializations, roughly 15 languages, 6 approved consultants with varied prices, specializations, timezones, and availability, 1 pending and 1 rejected consultant, 3 clients, and a spread of appointments in every status.

**Validation requirements.** Enum values in the schema match the constants in `config/` exactly. The seed validates its own inputs and refuses to run against a non-empty database unless `NODE_ENV !== 'production'` and an explicit `--force` flag is passed.

**Authorization requirements.** The application database role gets DML but not DDL rights; migrations use `DIRECT_URL` with the privileged role. Documented in the README here, applied in production in Step 23.

**Error handling.** Connection failures surface as a startup error naming the host and database but never the password.

**Testing requirements.** `tests/helpers/db.ts` provides per-suite isolation (fresh schema or transaction rollback). Database tests assert that: both exclusion constraints exist and reject overlapping inserts; a `CANCELLED` appointment does **not** block a new one at the same time; each CHECK constraint rejects its bad value; `Review.appointmentId` is unique; deleting a `User` cascades to sessions and profiles but is restricted while appointments exist; deleting a `Specialization` is restricted while referenced.

**Acceptance criteria.**

- `pnpm db:reset && pnpm db:seed` produces a working dataset from empty.
- Two raw inserts of overlapping `CONFIRMED` appointments for one consultant: the second fails with SQLSTATE `23P01`.
- `prisma migrate deploy` against an empty database reproduces the full schema including the hand-written constraints.
- `pnpm typecheck` passes with the generated client.
- Database tests pass in CI against a real PostgreSQL instance.

**Expected git commit message.**
`feat(db): add Prisma schema, constraints, and deterministic seed`

# Step 4 — Authentication

**Objective.** Implement registration, login, logout, session management, email verification, and password reset with database-backed sessions.

**Why it is needed.** Every protected surface depends on knowing who the caller is. This is the first step that produces a user-visible feature and the foundation for all authorization.

**Dependencies.** Steps 2 and 3.

**Files created or modified.**

- Dependencies: `@node-rs/argon2` (or `argon2`), `react-hook-form`, `@hookform/resolvers`.
- Created: `server/auth/{password,tokens,session,dal}.ts`, `server/services/auth.ts`, `schemas/auth.ts`, `features/auth/{login-form,register-form,forgot-password-form,reset-password-form,role-choice}.tsx`, `features/auth/actions.ts`, `app/(auth)/layout.tsx`, `app/(auth)/login/page.tsx`, `app/(auth)/register/page.tsx`, `app/(auth)/forgot-password/page.tsx`, `app/(auth)/reset-password/[token]/page.tsx`, `app/(auth)/verify-email/[token]/page.tsx`, `config/security.ts`.
- Modified: `.env.example` and `config/env.ts` (`SESSION_COOKIE_NAME`, `SESSION_TTL_DAYS`), `components/layout/site-header.tsx` (auth-aware menu).

**Database changes.** None — `User`, `Session`, and `VerificationToken` already exist.

**API changes.** No Route Handlers; `/api/auth/*` is deliberately not created. Server Actions: `registerAction`, `loginAction`, `logoutAction`, `logoutAllAction`, `requestPasswordResetAction`, `resetPasswordAction`, `verifyEmailAction`, `resendVerificationAction`.

**UI changes.** An auth shell (centered card, wordmark, back-to-home link). A login form. A registration form with an explicit role choice between "I am looking for support" and "I am a consultant", password strength feedback, and a terms checkbox. Forgot-password and reset-password forms. A verification-pending banner in the app shell with a resend action. The header shows the user menu when signed in.

**Business logic.** Exactly ARCHITECTURE.md §9: email lowercased and trimmed; Argon2id with the parameters pinned in `config/security.ts`; constant-work login including a dummy hash comparison when the user does not exist; lockout after 10 failures for 15 minutes; a 32-byte random session token stored only as its SHA-256 hash; 7-day absolute expiry with sliding renewal after 24 hours of use; revocation on logout, password change, and sign-out-everywhere; single-use, hashed, TTL-bounded verification and reset tokens; the user and profile created in one transaction; an `EmailOutbox` row queued for verification and reset mail (delivery arrives in Step 18 — until then a development-only log line prints the link).

**Validation requirements.** `schemas/auth.ts` with `registerSchema` (email, password of at least 12 characters mixing classes, confirmation match, full name 2–100, role in {`CLIENT`, `CONSULTANT`}, terms accepted, IANA timezone captured from the browser), `loginSchema`, `requestResetSchema`, `resetPasswordSchema`, and `tokenParamSchema`. Both the form (through `zodResolver`) and the action parse; the action's parse is authoritative.

**Authorization requirements.** All auth actions are public by design. `ADMIN` is rejected as a registration role at the schema level, not only in the UI. Signed-in users visiting `/login` or `/register` are redirected to their dashboard.

**Error handling.** Generic, enumeration-resistant responses on register, login, and reset request. Field-level errors for shape problems. `ACCOUNT_LOCKED` states when the lock lifts. Invalid, expired, or consumed tokens render a dedicated page offering a fresh link. Rate-limit trips return a friendly message with a retry hint.

**Testing requirements.** Unit: password hash and verify round-trip, token generation and hashing, session expiry arithmetic, lockout arithmetic. Integration: registration creates user, profile, and token in one transaction and rolls back completely on failure; a duplicate email returns the generic response and creates nothing; successful login writes a session row and sets a cookie with `httpOnly`, `secure`, and `sameSite=lax`; a wrong password increments the counter and the eleventh attempt is locked; renewal extends both row and cookie; logout revokes; password reset consumes the token, changes the hash, and revokes all sessions; a consumed token is rejected. E2E: register → verify → sign in → sign out.

**Acceptance criteria.**

- A new client can register, follow the verification link (logged in development), verify, sign out, and sign back in.
- The session cookie carries the required flags, and its token appears nowhere in the database in plaintext.
- Wrong credentials, a locked account, and an unknown email are indistinguishable in the response.
- Deleting a session row signs that browser out on its very next request.
- All listed tests pass.

**Expected git commit message.**
`feat(auth): add credentials auth with database-backed sessions`

# Step 5 — Authorization, RBAC, and route protection

**Objective.** Put the permission matrix into code, add the guards every subsequent step uses, protect the role-scoped route groups, and build the role dashboard shells.

**Why it is needed.** Every feature from Step 6 onward is role-scoped. Building the guards once — and testing them against the matrix — is what keeps authorization from being re-invented, and mis-invented, per feature.

**Dependencies.** Step 4.

**Files created or modified.**

- Created: `config/roles.ts` (the permission matrix as data), `server/authz/{policy,guards}.ts`, `proxy.ts`, `app/(client)/layout.tsx`, `app/(consultant)/layout.tsx`, `app/(admin)/layout.tsx`, `app/(client)/dashboard/page.tsx`, `app/(consultant)/consultant/page.tsx`, `app/(admin)/admin/page.tsx`, `components/layout/{app-shell,sidebar-nav,user-menu}.tsx`, `app/forbidden/page.tsx`, `config/nav.ts`, `tests/integration/authz.matrix.test.ts`.
- Modified: `server/auth/dal.ts` (add `requireUser`).

**Database changes.** None.

**API changes.** None.

**UI changes.** Three role shells sharing one `AppShell` primitive with different navigation sets: client (Dashboard, Appointments, Profile, Notifications), consultant (Dashboard, Profile, Availability, Appointments, Reviews), admin (Overview, Consultants, Users, Appointments, Specializations, Audit log). Each dashboard renders a real greeting plus placeholder cards that later steps fill in. A `/forbidden` page for the cases where 403 is the honest answer.

**Business logic.** The guards from ARCHITECTURE.md §10: `requireUser`, `requireRole`, `requireClient`, `requireConsultant({ approved })`, `requireAdmin`, `requireVerifiedEmail`, `assertOwnsAppointment`, `assertOwnsProfile`. Unauthenticated access to a protected page redirects to `/login?next=<path>`; wrong-role access renders 403; a suspended user is signed out with an explanation. `proxy.ts` exports a function named `proxy`, performs a cookie-presence check only (no database read — it runs on prefetches), handles redirects for `/dashboard`, `/appointments`, `/profile`, `/notifications`, `/consultant/*`, and `/admin/*` plus the reverse redirect off `/login` and `/register`, and generates the `x-request-id` correlation header.

**Validation requirements.** The `next` redirect parameter is validated as a same-origin relative path — it must start with `/` and must not start with `//` — before being used, preventing open redirects.

**Authorization requirements.** This step _is_ the authorization requirement. The rule it establishes, which every later step follows: page-level guards exist for UI correctness; the authoritative check lives in the service the action calls.

**Error handling.** A thrown `AuthorizationError` renders the 403 page; `AuthenticationError` redirects to login preserving the destination. Both are logged at `warn` with actor, route, and reason.

**Testing requirements.** A matrix-driven integration suite generated from `config/roles.ts`: for every role × capability cell, assert allow or deny. Unit tests for the `next` validator including `//evil.com` and `https://evil.com`. E2E: a client hitting `/admin` and `/consultant`, a consultant hitting `/admin`, and an anonymous user hitting `/dashboard` then being returned there after signing in.

**Acceptance criteria.**

- Each role reaches only its own shell, and every cross-role attempt is denied by the server rather than merely hidden.
- Signing in from a guarded page returns the user to that page.
- `//evil.com` as `next` does not redirect off-site.
- The matrix suite covers every capability in ARCHITECTURE.md §10 with no skipped cell.

**Expected git commit message.**
`feat(authz): add RBAC guards, route protection, and role shells`

# Step 6 — Client profiles

**Objective.** Let a client view and edit their profile — display name, contact details, timezone, languages, optional emergency contact — plus change password, sign out everywhere, and delete the account.

**Why it is needed.** Booking needs a client profile row, a display name to show the consultant, and a timezone to render times correctly. It is also the smallest complete feature slice and therefore proves the action → service → DAL pattern end to end.

**Dependencies.** Step 5.

**Files created or modified.**

- Created: `server/services/clients.ts`, `server/dal/client-profile.ts`, `schemas/client-profile.ts`, `features/profile/{profile-form,security-section,danger-zone,timezone-select,language-multiselect}.tsx`, `features/profile/actions.ts`, `app/(client)/profile/page.tsx`, `app/(client)/profile/loading.tsx`.
- Modified: `app/(client)/dashboard/page.tsx` (profile completeness prompt), `config/nav.ts`.

**Database changes.** None. One thing to verify here: the Step 4 registration transaction must already create the `ClientProfile` row. If it does not, fix it in this step rather than working around a missing row.

**API changes.** Server Actions: `updateClientProfileAction`, `changePasswordAction`, `requestAccountDeletionAction`. `logoutAllAction` from Step 4 is surfaced in this UI.

**UI changes.** `/profile` in three sections: personal details (display name, full name, phone, date of birth, timezone, preferred languages), security (change password, active session count, sign out everywhere), and a danger zone (delete account behind a typed confirmation). The timezone select is seeded from `Intl.supportedValuesOf('timeZone')` with the browser's zone pre-selected.

**Business logic.** Profile updates touch only the caller's own row. Changing the timezone affects display only — no stored instant moves. Changing the password verifies the current one, re-hashes, and revokes all other sessions while keeping the current one. Account deletion is the soft-delete-plus-anonymization procedure in ARCHITECTURE.md §17, refused while the user has a `PENDING` or `CONFIRMED` future appointment, with a message naming those appointments.

**Validation requirements.** `clientProfileSchema`: displayName 2–50, fullName 2–100, phone optional E.164, dateOfBirth optional and at least 16 years ago, timezone in the IANA set, every language id active. `changePasswordSchema` with current, new, and confirmation fields.

**Authorization requirements.** `requireClient()` on the page; the service takes the actor and filters every query by `userId: actor.id`. No code path accepts a profile id from the client.

**Error handling.** Field-level errors return to the form. A concurrent-update conflict re-reads and asks the user to retry. A deletion refusal explains exactly which appointments block it and links to them.

**Testing requirements.** Unit: age validation and phone normalization. Integration: an update touches only the caller's row; a forged profile id in the payload is ignored because no such field exists; a password change revokes other sessions but not the current one; deletion is refused with a future appointment and, when allowed, anonymizes the user while the appointment rows survive. E2E: edit the profile and see the change on the dashboard.

**Acceptance criteria.**

- A client can edit every field and the change persists and re-renders.
- Client A cannot modify client B's profile through any request shape.
- Changing the password signs out other sessions and keeps the current one.
- Deleting an account with a future appointment is refused with an actionable message.

**Expected git commit message.**
`feat(client): add client profile management and account settings`

**Objective.** Implement appointment creation, cancellation, and rescheduling with database-enforced overlap prevention, correct transaction boundaries, and safe concurrency behaviour.

**Why it is needed.** It is the product. Everything before this step is preparation; everything after is a view onto its output.

**Dependencies.** Steps 6, 10, and 11.

**Files created or modified.**

- Created: `server/services/booking.ts`, `server/dal/appointment.ts`, `schemas/booking.ts`, `features/booking/{booking-confirmation,booking-summary,note-field,policy-notice,cancel-dialog,reschedule-flow}.tsx`, `features/booking/actions.ts`, `app/(client)/consultants/[slug]/book/page.tsx`, `tests/integration/booking.concurrency.test.ts`.
- Modified: `features/booking/slot-picker.tsx` (selection leads to booking), `app/(marketing)/consultants/[slug]/page.tsx` (sign-in redirect that preserves the chosen slot), `server/errors.ts` (booking error codes and the PostgreSQL `23P01` mapping).

**Database changes.** None — every constraint was created in Step 3. This step verifies the `23P01` surface through Prisma and pins it with a test.

**API changes.** Server Actions: `createAppointmentAction`, `cancelAppointmentAction`, `rescheduleAppointmentAction`.

**UI changes.** `/consultants/[slug]/book` as a dedicated confirmation page — linkable and refresh-safe — showing the consultant, the slot in both timezones, duration, consultation type, price, the cancellation policy in plain words, and the optional note field with its visibility explained. Success redirects to the appointment detail page. A cancel dialog states the policy and the consequence. A reschedule flow reuses the slot picker and shows old against new.

**Business logic.** Exactly ARCHITECTURE.md §18. The create path: rate limit → parse → `requireClient()` and `requireVerifiedEmail()` → transaction (load the consultant `FOR SHARE` and check approved, active, accepting, and offering the requested type → recompute availability for the requested instant → check lead time, maximum advance, and the current time taken from the database → insert the appointment with price, duration, and timezone snapshots and the idempotency key → insert notification rows) → `updateTag('availability:{consultantId}')` plus the caller's appointment tags → redirect. Status is `CONFIRMED` when the consultant has `autoConfirmBookings`, otherwise `PENDING`. Cancellation applies the window rule to clients (BR-8) and offers "request cancellation" inside the window instead of hard-failing. Rescheduling is a cancel plus a create in one transaction linked by `rescheduledFromId`, bounded by `maxReschedules`. Every status change is compare-and-set.

**Validation requirements.** `createAppointmentSchema`: consultant slug, `startsAt` as an ISO instant aligned to the consultant's slot grid, a consultation type that consultant offers, note at most 1000 characters, idempotency key as a UUID. `cancelAppointmentSchema`: appointment id and a reason of at most 500 characters, required for consultant and admin cancellations. `rescheduleSchema`: appointment id plus the new instant, validated exactly as creation is.

**Authorization requirements.** Creation: the actor is the client and the appointment is created for their own profile — the client id comes from the session, never from the payload. Cancellation: the actor must be the booking client, the owning consultant, or an admin, with ownership expressed in the `where` clause. Reschedule: participants only. Reading an appointment filters by participation and returns 404 on a miss, which is the IDOR defence.

**Error handling.** `SLOT_TAKEN` (the consultant-key exclusion violation) re-renders the picker with fresh slots inline. `CLIENT_DOUBLE_BOOKED` explains the conflict and links to the existing appointment. `SLOT_NOT_AVAILABLE`, `SLOT_IN_PAST`, `LEAD_TIME_VIOLATION`, `TOO_FAR_AHEAD`, `CONSULTANT_UNAVAILABLE`, `CANCELLATION_WINDOW_CLOSED`, `INVALID_STATE`, and `RESCHEDULE_LIMIT_REACHED` each map to a specific, actionable message. A repeated idempotency key returns the original appointment as success. No automatic retry ever silently books a different time.

**Testing requirements.** Integration: the happy path for both auto-confirm settings; every rejection path above; booking outside published availability; booking in the past; booking while the consultant is pending, rejected, suspended, or not accepting; cancelling inside and outside the window for each actor; rescheduling successfully and into a taken slot; the reschedule limit; an idempotent double submit. **Concurrency:** ten parallel `createAppointmentAction` calls on the same slot must yield exactly one appointment and nine `SLOT_TAKEN` results; a cancellation racing a booking on the freed slot must leave exactly one active appointment; two parallel reschedules into the same target slot must leave one winner. Database: a cancelled appointment does not block re-booking. E2E: the full client booking journey, and the "someone took it" recovery path.

**Acceptance criteria.**

- A client can book, cancel, and reschedule end to end.
- The concurrency test passes on 20 consecutive runs in CI with exactly one winner every time.
- No booking can be created in the past, outside availability, or with a non-approved consultant.
- A client cannot read or cancel another client's appointment; the attempt returns 404.
- Cancelling immediately frees the slot for another client.

**Expected git commit message.**
`feat(booking): add appointment creation, cancellation, and rescheduling`
